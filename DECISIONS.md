## Dependency injection: Hilt

Originally planned hand-rolled DI (fewer moving parts, lower setup risk in a timeboxed exercise). Reversed after deciding to build this as something meant to be extended rather than a one-shot submission: Hilt's KSP setup cost is cheap to pay now, while it's still just a dependency-wiring step, and gets expensive to retrofit once more classes exist. It also makes swapping fakes for production bindings in tests mechanical (`@Module` + `@TestInstallIn`) rather than manual constructor-threading, which matters more as the class count grows.

**Build-tooling side effect:** wiring up Hilt surfaced that this project was relying on AGP 9's new "built-in Kotlin" compilation mode, which KSP (and therefore Hilt) doesn't yet support — [open upstream issue](https://github.com/google/ksp/issues/2729), unresolved as of Dec 2025. Fixed by opting back into the classic `org.jetbrains.kotlin.android` Gradle plugin (`android.builtInKotlin=false` / `android.newDsl=false` in `gradle.properties`), which then needed an explicit `jvmTarget` set to match `compileOptions` (11). Google's docs say this opt-out is removed in AGP 10 — worth rechecking KSP/AGP compatibility before any future AGP upgrade past 9.

## Logging: Timber

Added over raw `Log`/`println`. Geofence and BLE transitions are timing-sensitive and, per the prompt's own setup-constraint warning, often only reproducible on real hardware with the app fully backgrounded and no debugger attached — `Timber.d(...)` piped to `adb logcat` is the practical way to see what the state machine did when there was no UI alive to observe it directly.

## Where test fakes live: `src/test/java/.../fakes/`

Considered three placements: alongside the interface/impl in the main source set, in a dedicated `src/test/.../fakes/` package, or in an AGP `testFixtures` source set (the mechanism meant for fakes shared between `test` and `androidTest`). Picked `src/test/.../fakes/` — every unit specified in the "Testability" section (containment, RSSI smoothing, beacon-lost timeout, the state machine including EXIT-stops-scanning) is pure Kotlin exercised by JVM unit tests; nothing calls for an instrumented test, and the prompt's own simulation section confirms the real BLE/geofence integration path can only be verified on physical hardware anyway, not via `androidTest`. `testFixtures` is the correct move if that ever changes, but not worth the extra source-set setup pre-emptively here.

## Release optimization (R8) and `testFixtures`: investigated, not changed

Both tested empirically (temporarily flipped on, measured/observed, reverted — nothing shipped). Full detail in `planning.md` §15/§16.

- **R8 (`optimization.enable`):** works, but on this project's AGP version (9.2.1) needs an extra `android.r8.gradual.support=true` flag the simplified DSL doesn't need starting AGP 9.3. With it on: unoptimized release APK 23.7 MB vs. optimized 1.69 MB, no R8 warnings against the current dependency set. Left off for now — minified builds are harder to debug mid-development (de-obfuscation required, silent runtime failures instead of compile errors for anything under-covered by keep rules); flip on later, right before the build that actually ships. Also surfaced an unrelated pre-existing issue, since fixed during scaffolding: `compileSdk` was bumped `36.1 → 37` (`androidx.core:core-ktx:1.19.0` and `androidx.lifecycle:lifecycle-runtime-compose-android:2.11.0` require 37) — `checkDebugAarMetadata`/release builds/`androidTest` compiles are unblocked now.
- **`testFixtures`:** works on an application module (not library-only, despite some docs suggesting otherwise), but Kotlin sources in it need an experimental flag (`android.experimental.enableTestFixturesKotlinSupport=true`, silently skips `.kt` files without it) and this project's project-wide Compose compiler plugin then fails on the testFixtures compile task unless Compose deps are separately added to `testFixturesImplementation` — friction with no present payoff, since §15 above already established nothing here needs `androidTest`-shared fakes. Confirms the `src/test/.../fakes/` decision rather than changing it.

## "Already inside" (requirement 2): combined manual check + INITIAL_TRIGGER_ENTER backstop

Decided and wired into the manual test UI, driven by a real symptom: registering geofences and then standing inside one showed nothing in the geofence log for a noticeable delay (up to a couple minutes) before Play Services' own `INITIAL_TRIGGER_ENTER` evaluation caught up — it uses whatever location fix it already has, not necessarily a fresh one, so the delay is inherent to relying on it alone.

Fix, in `VenueViewModel.registerGeofences()`: alongside the real `geofenceSource.registerVenues()` call (which keeps `INITIAL_TRIGGER_ENTER` registered as the backstop for real-world crossings and process-death recovery), immediately fetch a fresh fix via `LocationSource.currentLocation()` and check it against every venue with `ContainmentChecker.isWithin()` — any venue already inside gets logged right away instead of waiting on the OS's own timing. `FusedLocationSource`/`ContainmentChecker` already existed and were tested in isolation, but weren't actually wired into the registration flow until now — that was the reason this took as long as it did on real hardware.

De-duplication: since both paths can independently report the same ENTER (the fast manual check, then the slower official one catching up), `onGeofenceTransition` tracks `insideVenueIds` and only logs on an actual state change (`Set.add()`/`remove()` returning false means no-op) — this guards the *log* specifically; the actual `VenueState`/scanning idempotency is now handled by `VenueStateMachine.reduce()` itself (see "Scanning gated on geofence presence" below), which `onGeofenceTransition` feeds once the log-level dedup has passed.

## Scanning gated on geofence presence (requirement 4), register-on-init

Implemented for real, replacing the manual Start/Stop Scanning button and the "Register Geofences" button from earlier testing passes:

- **Register on init, not behind a button.** `registerGeofences()` runs automatically if `ACCESS_FINE_LOCATION` is already granted (checked via the new `PermissionChecker` abstraction below); `VenueScreen` requests the needed permissions on first launch via `LaunchedEffect(Unit)` and calls `registerGeofences()` again on grant, covering the not-yet-granted case. `registerGeofences()` stays idempotent, so the double-call in the "already granted" path is harmless.
- **Scanning starts on confirmed ENTER, stops on EXIT — never runs while outside every venue**, per requirement 4. Both geofence transitions and BLE sightings route through the real `VenueStateMachine.reduce()` (previously injected but unused) instead of parallel ad-hoc tracking: `onGeofenceTransition` turns a de-duplicated `Entered`/`Exited` into `VenueEvent.Enter`/`Exit`, reduces against the current `VenueState`, and — only on an actual state change (`updated !== previous`, matching the reducer's reference-equality no-op contract) — starts/retargets/stops the scanner based on `updated.venueOrNull()`. BLE sightings become `VenueEvent.BeaconSeen(smoothedRssi)` the same way, so `currentReading` and the state genuinely reflect Outside/Inside(venue)/InRange(venue, proximity, rssi) rather than a separately-tracked scanning flag.
- **Permission gated with graceful degradation (requirement 8):** if `BLUETOOTH_SCAN`/`ACCESS_FINE_LOCATION` isn't granted when a venue is entered, starting the scan no-ops instead of crashing — the geofence state (and its log entry) still updates correctly, just without a live beacon reading.

**New: `PermissionChecker` abstraction.** Gating scan-start on permission meant something needed to check permission state itself (not just request it, which stays in `VenueScreen` where `ActivityResultLauncher` lives). Calling `ContextCompat.checkSelfPermission` directly would have required Robolectric to unit-test — added `data/permission/PermissionChecker.kt` (interface) + `AndroidPermissionChecker` (impl, `@ApplicationContext`-backed) + `FakePermissionChecker` in tests, matching the same interface-at-the-boundary pattern already used for `GeofenceSource`/`BleScanner`/`LocationSource`. Small addition, but keeps the whole flow — including the new "no permission → no-op" behavior — plain-JUnit-testable.

## Scanning ownership moved from VenueViewModel to VenueMonitor (a singleton)

The above was originally built directly in `VenueViewModel`. Real-device testing (foreground the whole time, geofence ENTER/EXIT correctly reflected on app launch via the "already inside" fast path, but *not* picking up a real leave/re-enter afterward) surfaced the actual problem: `VenueMonitorService` — the foreground service meant to protect the process from being killed while Inside a venue — was **only ever started by a real, OS-delivered geofence broadcast**, never by the fast "already inside" check. Since the fast check is what almost always establishes the visible initial state (it's near-instant vs. the OS's opportunistic `INITIAL_TRIGGER_ENTER`), the app frequently ended up "looking correct" while holding zero process protection — any later transition arriving while the process was killed was silently and permanently lost (`MutableSharedFlow` has no replay).

Root-caused further: even with the service correctly protecting the process, `VenueViewModel` owned all the scanning/state logic — meaning it was tied to the **Activity's** lifecycle, not the geofence-monitoring session's. That's backwards for a requirement whose entire premise (per the take-home's own framing of requirement 9) is "a transition can fire when the app has no UI alive."

Fix: moved all of it — `VenueStateMachine` orchestration, BLE scan start/stop, RSSI smoothing, beacon-lost timing, both logs, `isScanning` — out of `VenueViewModel` into a new `@Singleton` `domain/VenueMonitor.kt`, which lives for the app process's lifetime, independent of any Activity/ViewModel. `VenueViewModel` is now a thin pass-through that just hands `VenueMonitor`'s `StateFlow`s to Compose (Hilt ViewModels are still the idiomatic way to do that). `VenueMonitorService` also simplified to match: it holds zero business logic now, purely the foreground-service protection — the actual scan coroutine executes in `VenueMonitor`, not the service, specifically so it stays plain-JUnit-testable without Robolectric (an Android `Service` is hard to unit test directly).

**New: `ServiceStarter` abstraction**, same reasoning as `PermissionChecker` — `VenueMonitor.registerGeofences()`'s fast path now also starts the protective foreground service itself (closing the gap above), via `data/service/ServiceStarter.kt` (interface) + `AndroidServiceStarter` (impl) + `FakeServiceStarter` (tests), rather than injecting a raw `Context` and losing testability.

**A real correctness constraint surfaced while doing this, worth remembering:** `GeofenceBroadcastReceiver`'s own `context.startForegroundService(...)`/`stopService(...)` calls were deliberately left exactly where they are (synchronous, inside `onReceive()`) rather than routed through `VenueMonitor`/`ServiceStarter` too. Android's Android-12+ background-foreground-service-start exemption for system-triggered broadcasts only covers the receiver's own call stack during `onReceive()` — deferring the call to an async coroutine callback (even one scheduled milliseconds later, e.g. inside `VenueMonitor`'s transitions collector) would fall outside that exemption and could throw `ForegroundServiceStartNotAllowedException` when the app is genuinely backgrounded, which is exactly the scenario this whole mechanism exists for. `VenueMonitor`'s fast path is safe to call `ServiceStarter` directly instead, because it only ever runs while the app is being actively viewed (app launch / permission grant), which is unconditionally exempt regardless of trigger source.

**Added a scanning/not-scanning indicator to `VenueScreen`** (separate from the `currentReading` text) as a sanity-check — lets you see at a glance whether the radio is actually on, independent of what the proximity text says, while verifying this on real hardware.

**Resolved: real geofence EXIT/re-ENTER crossings take 2–5 minutes to fire on real hardware.** Not a bug, and not the process-lifecycle issue above — a longer, patient real-device test (waiting in place for several minutes rather than checking within seconds/a minute of crossing) confirmed transitions eventually arrive correctly. Consistent with everything already known about Play Services geofencing being opportunistic rather than event-driven-on-crossing (same root cause as the earlier "already inside" delay, and consistent with a 50m radius sitting below Google's own recommended 100–150m minimum). **Practical implication for testing and the eventual README/demo recording:** budget several minutes of waiting in place after each geofence crossing before concluding a transition didn't fire — this is inherent OS latency, not something the app controls or can meaningfully speed up further.

Along the way, restored a permanent diagnostic aid worth keeping regardless: `GeofenceBroadcastReceiver` now logs the real ENTER/EXIT it receives from the OS (previously only error paths logged anything), and `VenueMonitor` mirrors every processed transition to Timber alongside the in-memory `_geofenceLog`, plus logs once when the singleton itself is (re)created. Logcat persists across a process restart where the in-app log doesn't, so this is what actually let this get diagnosed — comparing the receiver's "real ENTER/EXIT" lines against `VenueMonitor`'s processed lines, and counting "VenueMonitor created" lines to spot restarts, rather than trusting the volatile in-app log alone.

**Known gap, flagged not fixed — overlapping geofences.** `VenueState` tracks at most one venue at a time (`Inside(venue: Venue)`, not a set). Real symptom from manual testing: two of this project's venues (50m radius each) are only ~71.5m apart, and since 71.5m < 100m (sum of both radii), their geofences genuinely overlap. Standing in the overlap zone and entering the second venue while still inside the first just switches `VenueState` to the second venue (`VenueStateMachine.onEnter`) — the first venue's still-active membership is silently dropped from tracking. Leaving the second venue's radius while still inside the first's then produces an incorrect `Outside` instead of falling back to `Inside(first)`, since the app already lost track of it. Documented in a comment on `VenueState.venueOrNull()` and referenced from `VenueStateMachine.onEnter`/`onExit`. Needs a real design pass (e.g. `VenueState` holding a `Set<Venue>` instead of a single `Venue`, with the reducer and the scan-target logic in `VenueViewModel` both updated to match) before this is solid for venues that can geographically overlap — not attempted here, out of scope for this pass.

## Beacon format: iBeacon

Decided: iBeacon (UUID + major + minor). Briefly switched to Eddystone-UID — it gets a marginally cleaner `setServiceUuid(0xFEAA)` filter dimension than iBeacon's manufacturer-data-only option, at the cost of one extra edge case (UID/URL/TLM sibling frames sharing the same service UUID). Reverted to iBeacon: the take-home spec names it directly as its first example beacon-identity format, which settles it over a functionally-comparable alternative — not worth diverging from the example for a marginal filtering-cleanliness edge. Full comparison in `planning.md` §3.

This matches the scaffolded stub code (`BeaconIdentity`, `VenueRepository`, `PlatformBleScanner`'s comment already model the iBeacon shape) — no rework needed there.

## RSSI smoothing: moving average (window 5)

Decided, over EMA or median — simple, testable with fixture data, and the 4-bucket proximity output (Immediate/Near/Far/Unknown) doesn't have enough resolution to justify EMA's tuning knob. Reasoning in `planning.md` §6.

**Beacon-lost timeout: N = 5s (decided, revised from an earlier 10s lean).** Implemented in `BeaconLostTimer` (`domain/BeaconLostTimer.kt`) — reset on every `beaconSeen()`; if nothing arrives within `N`, `lost` flips to true (and recovers automatically the next time a sighting comes in). `N` is a hardcoded constant (`DEFAULT_BEACON_LOST_TIMEOUT`) for this exercise, with a comment flagging it as a reasonable candidate for remote config or a user preference rather than a fixed app-wide value if this ever became a real product — different venues/environments might reasonably want different sensitivity. Wired into the manual BLE-test harness (`VenueViewModel`) so a lost beacon now surfaces as `Proximity.UNKNOWN` in the current-reading text and the log, rather than latching the last reading forever, per requirement 5. Covered by dedicated tests (`BeaconLostTimerTest`, using `kotlinx-coroutines-test`'s virtual time) plus two scenario tests through `VenueViewModel`.

## Foreground service decision: foreground-only-while-Inside

Decided: `BroadcastReceiver` calls `startForegroundService()` on confirmed ENTER, `VenueMonitorService.stopSelf()` on confirmed EXIT — the service's lifetime is tied to the same Inside/Outside gate as the scanner itself, rather than an always-on foreground service or a plain background service. A plain background service was ruled out specifically because requirement 9's scenario (geofence transition firing with no UI alive) is exactly the condition Android's background execution limits and BLE scan throttling target — it risks silently going dark partway through an Inside session. Full option comparison and the background-service reasoning are in `planning.md` §8/§14.

Implementation notes carried over from planning: `startForeground()` must be called immediately in the service (no async setup first, see the §5 PendingIntent/background-start gotcha), and the manifest needs `FOREGROUND_SERVICE_CONNECTED_DEVICE` declared with `foregroundServiceType="connectedDevice"`.

## Location permission still required despite `BLUETOOTH_SCAN`'s `neverForLocation`

Verified on real hardware. §11's assumption that declaring `BLUETOOTH_SCAN` with `android:usesPermissionFlags="neverForLocation"` removes the need for `ACCESS_FINE_LOCATION`/Location Services did not hold on the test device — scan results were silently empty until `ACCESS_FINE_LOCATION` was also granted, even with `BLUETOOTH_SCAN` granted. Matches real-world reports that this exemption is inconsistently honored across OEM Bluetooth stacks. Fixed in `VenueScreen.kt`: request both `BLUETOOTH_SCAN` and `ACCESS_FINE_LOCATION` together on API 31+ (not either/or), gate scanning on both being granted, and check before every scan start rather than only once at first composition.

This was also the actual explanation for an earlier, separate-looking symptom: `PlatformBleScanner`'s radio-level `ScanFilter.setManufacturerData(id, data, mask)` briefly appeared to silently drop every scan result and was removed mid-debugging in favor of unfiltered scanning + software-side matching. With the location permission fix in place, retesting confirmed the `ScanFilter` works fine — it's restored and in effect. The apparent "`ScanFilter` is unreliable" finding was a red herring caused by the same missing permission, not a real issue with the API.

## Proximity buckets replace raw RSSI in the manual BLE-test UI

Requirement 5 asks the app to "expose a coarse proximity bucket: Immediate / Near / Far / Unknown," not raw dBm. The manual test screen (`VenueViewModel`/`VenueScreen`) originally displayed raw + smoothed RSSI numbers instead, since it predates `VenueStateMachine.reduce()` being usable end-to-end. Swapped to show the `Proximity` bucket (distance-in-meters estimate kept alongside it). The RSSI→`Proximity` threshold logic was previously private inside `VenueStateMachine`; extracted to a shared top-level `proximityFor()` (`domain/ProximityClassifier.kt`) so both the state machine and the manual test screen use identical thresholds rather than risking two copies drifting apart.

## Module structure: stayed single-module

Considered splitting into a Gradle module per package (`:domain`, `:data-venue`, `:data-geofence`, `:data-ble`, `:data-location`, `:service`, `:ui`, plus `:app`) to better signal "built to extend." Estimated 3–5 hours for the full per-package split vs. 1.5–2.5 hours for a coarser 3-module version (`:domain`, `:data`, `:app`) — most of that cost is Gradle/Hilt friction, not moving files: this project already hit an AGP 9 "built-in Kotlin" vs. KSP incompatibility once (see Dependency injection above), and each additional Android library module carrying `@Inject`/`@Binds` would need the same fix repeated or centralized via a convention plugin; plus a real `api`/`implementation` visibility pass per dependency edge, and moving each fake into its owning module's own `test` source set instead of `:app`'s.

Decided against it, and kept the current single-module structure. Reasoning: the prompt is explicit that this is "one screen," 6–10 hours total, and structure is graded partly on *not* over-building — 8 Gradle modules for a single-screen app with no feature boundaries to enforce (there's nothing for a `:ui` or `:service` module to protect against) reads more like over-engineering than foresight to a reviewer, especially layered on top of a codebase that's still mostly `TODO()` stubs. A `:di` module also doesn't actually work as conceived — Hilt's `@Binds` graph needs to see every impl, so that wiring collapses back into `:app` regardless of how many modules exist below it. Full reasoning in the conversation; not written up in `planning.md` since nothing was implemented.

## Battery tradeoffs considered

- Scan filtering at the radio level (`ScanFilter` matching manufacturer data + UUID mask) rather than scanning unfiltered and discarding in the callback — cheaper than CPU-side filtering. Briefly removed mid-debugging on a misdiagnosis (see "Location permission" above), confirmed working and restored after the real root cause was found and fixed.
- Foreground-service-only-while-Inside instead of always-on, so the radio/scanner overhead is bounded to the time actually spent inside a venue.
- Activity Recognition as an optional stretch goal to duty-cycle scan aggressiveness (`LOW_LATENCY` while walking, `BALANCED`/`LOW_POWER` while still) — explicitly not required, only attempted if time remains; see `planning.md` §9.

## What I'd do with another week

To be filled in more fully once the core implementation is further along — premature to speculate in depth before the pending decisions above are settled and something is actually built against them. Items already known:

- Revisit the coarse 3-module split (`:domain`, `:data`, `:app`) above once the interfaces have stopped moving — worth doing once, not worth doing speculatively now.
- **Site-calibrated distance heuristics.** `DistanceEstimator`'s log-distance path-loss model (`domain/DistanceEstimator.kt`) uses a fixed generic `pathLossExponent` (default 2.0, free-space). A real venue has walls, shelving, bodies, other 2.4GHz traffic — all of which distort RSSI in ways a single hardcoded exponent can't capture. With more time, worth computing that exponent (or a richer per-venue calibration curve) from actual measurements taken in the real deployment space — e.g. walking a known distance from the beacon and fitting the curve to observed RSSI — rather than assuming one constant works everywhere. Would meaningfully improve proximity-bucket accuracy in real, interference-heavy environments instead of just the open-air conditions this was tested in.
- More generally: this is a first pass, and there are almost certainly other real improvements worth making once there's usage/data to learn from — this list isn't meant to be exhaustive, just what's visible from here.
