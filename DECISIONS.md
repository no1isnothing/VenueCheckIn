# Decisions

## Dependency injection: Hilt

Picked Hilt because it's familiar and common. Also, where possible, built the app as though someone might want to extend it at some point.

## Logging: Timber

Added over raw `Log`/`println`. Geofence and BLE transitions are timing-sensitive and, per the prompt's own setup-constraint warning, often only reproducible on real hardware with the app fully backgrounded and no debugger attached — `Timber.d(...)` piped to `adb logcat` is the practical way to see what the state machine did when there was no UI alive to observe it directly.

**Known gap, flagged not fixed — `Timber.DebugTree()` is planted unconditionally.** `VenueCheckInApplication.onCreate()` has the intended `if (BuildConfig.DEBUG) { ... }` gate commented out around `Timber.plant(Timber.DebugTree())`. Almost certainly because `buildFeatures.buildConfig` isn't enabled in `app/build.gradle.kts`, so `BuildConfig.DEBUG` wouldn't even compile as written. Net effect: verbose debug logging ships in every build variant, including release. Low-stakes here since release `optimization` is already off by deliberate choice (see below), but a real ship build would need `buildFeatures.buildConfig = true` (or an equivalent gating mechanism) to restore real debug-only logging.

## Release optimization (R8) and `testFixtures`: investigated, not changed

Not worthwhile for this exercise, but recorded in the planning doc.

## "Already inside" (requirement 2): combined manual check + INITIAL_TRIGGER_ENTER backstop

Decided to combine a manual check on startup with the geofence's `INITIAL_TRIGGER_ENTER` backstop, rather than relying on either one alone.
Added de-duplication since both paths can independently report the same ENTER (the fast manual check, then the slower official one catching up).

## Scanning ownership moved from VenueViewModel to VenueMonitor (a singleton)

The above was originally built directly in `VenueViewModel`. Real-device testing (foreground the whole time, geofence ENTER/EXIT correctly reflected on app launch via the "already inside" fast path, but *not* picking up a real leave/re-enter afterward) surfaced the actual problem: `VenueMonitorService` — the foreground service meant to protect the process from being killed while Inside a venue — was **only ever started by a real, OS-delivered geofence broadcast**, never by the fast "already inside" check. Since the fast check is what almost always establishes the visible initial state (it's near-instant vs. the OS's opportunistic `INITIAL_TRIGGER_ENTER`), the app frequently ended up "looking correct" while holding zero process protection — any later transition arriving while the process was killed was silently and permanently lost (`MutableSharedFlow` has no replay).

Root-caused further: even with the service correctly protecting the process, `VenueViewModel` owned all the scanning/state logic — meaning it was tied to the **Activity's** lifecycle, not the geofence-monitoring session's. That's backwards for a requirement whose entire premise (per the take-home's own framing of requirement 9) is "a transition can fire when the app has no UI alive."

Fix: moved all of it — `VenueStateMachine` orchestration, BLE scan start/stop, RSSI smoothing, beacon-lost timing, both logs, `isScanning` — out of `VenueViewModel` into a new `@Singleton` `domain/VenueMonitor.kt`, which lives for the app process's lifetime, independent of any Activity/ViewModel. `VenueViewModel` is now a thin pass-through that just hands `VenueMonitor`'s `StateFlow`s to Compose (Hilt ViewModels are still the idiomatic way to do that). `VenueMonitorService` also simplified to match: it holds zero business logic now, purely the foreground-service protection — the actual scan coroutine executes in `VenueMonitor`, not the service, specifically so it stays plain-JUnit-testable without Robolectric (an Android `Service` is hard to unit test directly).

**New: `ServiceStarter` abstraction**, same reasoning as `PermissionChecker` — `VenueMonitor.registerGeofences()`'s fast path now also starts the protective foreground service itself (closing the gap above), via `data/service/ServiceStarter.kt` (interface) + `AndroidServiceStarter` (impl) + `FakeServiceStarter` (tests), rather than injecting a raw `Context` and losing testability.

**A real correctness constraint surfaced while doing this, worth remembering:** `GeofenceBroadcastReceiver`'s own `context.startForegroundService(...)`/`stopService(...)` calls were deliberately left exactly where they are (synchronous, inside `onReceive()`) rather than routed through `VenueMonitor`/`ServiceStarter` too. The Android 12+ background-foreground-service-start exemption for system-triggered broadcasts only covers the receiver's own call stack during `onReceive()` — deferring the call to an async coroutine callback (even one scheduled milliseconds later, e.g. inside `VenueMonitor`'s transitions collector) would fall outside that exemption and could throw `ForegroundServiceStartNotAllowedException` when the app is genuinely backgrounded, which is exactly the scenario this whole mechanism exists for. `VenueMonitor`'s fast path is safe to call `ServiceStarter` directly instead, because it only ever runs while the app is being actively viewed (app launch / permission grant), which is unconditionally exempt regardless of trigger source.

**Added a scanning/not-scanning indicator to `VenueScreen`** (separate from the `currentReading` text) as a sanity-check — lets you see at a glance whether the radio is actually on, independent of what the proximity text says, while verifying this on real hardware.

**Resolved: real geofence EXIT/re-ENTER crossings take 2–5 minutes to fire on real hardware.** Not a bug, and not the process-lifecycle issue above — a longer, patient real-device test (waiting in place for several minutes rather than checking within seconds/a minute of crossing) confirmed transitions eventually arrive correctly. Consistent with everything already known about Play Services geofencing being opportunistic rather than event-driven-on-crossing (same root cause as the earlier "already inside" delay, and consistent with a 50m radius sitting below Google's own recommended 100–150m minimum). **Practical implication for testing and the eventual README/demo recording:** budget several minutes of waiting in place after each geofence crossing before concluding a transition didn't fire — this is inherent OS latency, not something the app controls or can meaningfully speed up further.

Along the way, restored a permanent diagnostic aid worth keeping regardless: `GeofenceBroadcastReceiver` now logs the real ENTER/EXIT it receives from the OS (previously only error paths logged anything), and `VenueMonitor` mirrors every processed transition to Timber alongside the in-memory `_geofenceLog`, plus logs once when the singleton itself is (re)created. Logcat persists across a process restart where the in-app log doesn't, so this is what actually let this get diagnosed — comparing the receiver's "real ENTER/EXIT" lines against `VenueMonitor`'s processed lines, and counting "VenueMonitor created" lines to spot restarts, rather than trusting the volatile in-app log alone.

**Known gap, flagged not fixed — overlapping geofences.** `VenueState` tracks at most one venue at a time (`Inside(venue: Venue)`, not a set). Real symptom from manual testing: two of this project's venues (50m radius each) are only ~71.5m apart, and since 71.5m < 100m (sum of both radii), their geofences genuinely overlap. Standing in the overlap zone and entering the second venue while still inside the first just switches `VenueState` to the second venue (`VenueStateMachine.onEnter`) — the first venue's still-active membership is silently dropped from tracking. Leaving the second venue's radius while still inside the first's then produces an incorrect `Outside` instead of falling back to `Inside(first)`, since the app already lost track of it. Documented in a comment on `VenueState.venueOrNull()` and referenced from `VenueStateMachine.onEnter`/`onExit`. Needs a real design pass (e.g. `VenueState` holding a `Set<Venue>` instead of a single `Venue`, with the reducer and the scan-target logic in `VenueViewModel` both updated to match) before this is solid for venues that can geographically overlap — not attempted here, out of scope for this pass.

`onGeofenceTransition` logs every raw ENTER/EXIT the geofence API delivers to the Geofence Log unconditionally (`"Geofence API: ENTER/EXIT received for <venue>"`), separate from `reconcileContainment`'s own `"Entered X"/"Exited X"` line (which still only logs on an actual confirmed state change) — needed for visibility into duplicate/stale events while diagnosing the above, and worth keeping permanently for the same reason `GeofenceBroadcastReceiver`'s Timber logging was.

## VenueMonitor process lifecycle: eager init, and what can (and can't) still interrupt it

**Known gap, flagged not fixed — swiping the app away from Recents kills the foreground service.** `VenueMonitorService` has no `android:stopWithTask="false"` in the manifest, so it defaults to `true`: removing the app's task from Recents stops the service (and shortly after, the process) immediately, with no `onTaskRemoved()` override to reschedule anything. This is an extremely common, everyday user gesture, not an edge case — arguably more likely in practice than an OS memory-pressure kill. Not attempted here; a real fix would need `stopWithTask="false"` plus either restarting the service from `onTaskRemoved()` or accepting the resulting process death and relying on the eager-init fix above plus a real geofence transition to recover.

**Known gap, flagged not fixed — geofence registrations don't survive a device reboot.** `GeofencingClient` registrations live in Play Services' in-memory state, not on disk, and are cleared on reboot. This app has no `BOOT_COMPLETED` receiver, so after any reboot, geofence monitoring silently stops until the user manually reopens the app and `registerGeofences()` runs again. Not attempted here; a real fix would add a manifest-registered `BroadcastReceiver` for `android.intent.action.BOOT_COMPLETED` (plus the corresponding permission) that calls `registerGeofences()`.

**Known non-issue — leaving `VenueMonitor` "running" indefinitely.** Worth being deliberate about, since "never shut anything down" is usually a smell: while `Outside`, `VenueMonitor`'s only ongoing work is `geofenceSource.transitions.collect { }`, a coroutine parked on a `Flow` doing nothing until an event arrives — no CPU, no battery, no wake lock, no active `sessionScope` (BLE scanning, `RssiSmoother`, `BeaconLostTimer`, `GeofenceBorderPoller` are all torn down by `stopScanning()` the moment state leaves `Inside`/`InRange`), and no foreground-service notification (that's separately gated to Inside-only). The only "cost" is a few small idle objects sitting in memory, which the OS's own process-priority/low-memory-killer mechanism reclaims on its own schedule regardless of anything the app does — a normal background process holding no wake lock or foreground service is exactly as killable as if we'd manually torn everything down first. Deliberately not adding an "idle timeout" that tears down the transitions collector after being away for a while: that's the one thing in this class that must never stop, since it's the only mechanism able to detect a return to a venue, and Android's natural process lifecycle (combined with the eager-init fix above) already provides the "shut down when actually idle, restart when actually needed" behavior for free.

## GeofenceBorderPoller: location-based border watch after beacon loss (could be expanded to run after all exit/enter events)

Real geofence EXIT can take 2–5 minutes to fire (see above), and scanning would otherwise keep running the whole time even if the user has clearly already left — which cuts against requirement 4's "must never be scanning while outside every venue." Since `ContainmentChecker` already existed for the "already inside" fast path, reused it here rather than building something new: once a beacon is lost (`BeaconLostTimer` fires), `GeofenceBorderPoller` starts polling actual location every `DEFAULT_GEOFENCE_BORDER_POLL_INTERVAL` (30s, configurable) via `LocationSource` + `ContainmentChecker`. Each poll's result is reconciled through the same `reconcileContainment` path (see above) a real geofence transition uses — not a parallel/duplicate implementation — so state, logging, and scan start/stop all go through one code path regardless of which source triggered it.

**Deliberately keeps running its full `DEFAULT_GEOFENCE_BORDER_POLL_MAX_DURATION` (5 minutes) window once triggered, regardless of subsequent beacon sightings** — previously it stopped itself as soon as the beacon reappeared. Removed that early-stop: a single beacon sighting isn't enough to justify tearing down a poller that might need to catch a *later* exit within the same window (e.g. exit → re-enter → exit again, all within a few minutes), and a fresh scanning session's own brand-new `BeaconLostTimer` starts at "not lost," which would otherwise stop it again immediately on every re-entry. **Tradeoff, worth being explicit about:** because of this, a single stale/low-accuracy location fix can now force an EXIT even while the beacon is actively being seen — see the GPS-accuracy gap below, which this makes slightly more consequential than before. Judged worth it: the alternative (stopping early) is exactly what caused the stuck-`Outside` bug, and a spurious EXIT here just triggers a quick, self-correcting EXIT→ENTER flip on the next poll rather than a permanent bad state, whereas a poller that stops too eagerly can end up with nothing watching at all.

Reused, not recreated, across repeated beacon-loss events for the same venue while a poller is already running (`start()` no-ops if still active) or after a prior window naturally expired (`start()` correctly resumes rather than resetting). A poller found running for a *different* venue when a new scanning session starts is stopped and discarded — handles the (already-known, unfixed) overlapping-geofence edge case from spilling stale state across venues.

Capped at `DEFAULT_GEOFENCE_BORDER_POLL_MAX_DURATION` (5 minutes) regardless — past that, the real Play Services API should be catching up on its own anyway, so further local polling has diminishing value while still costing a location fetch every interval. This cap was also what fixed a real, separate bug surfaced by a hanging test: the poller's loop shares `VenueMonitor`'s `TestCoroutineScheduler` in tests (via `Dispatchers.Main.immediate`), and a scenario that left it running forever (beacon lost, never confirmed outside, never restarted) made `runTest`'s own cleanup hang trying to drain a scheduler with a genuinely-infinite task on it. `VenueMonitor.cancelForTesting()` was also added as a defense-in-depth teardown hook for tests regardless.

Tradeoff (see "Battery tradeoffs considered" below): this adds a location fetch on top of the existing geofence machinery, but only while a beacon has already gone quiet (not continuously) — and it's what actually makes the "never scanning while outside" requirement hold in practice, rather than in theory, given how slow real geofence EXIT is.

**Known gap, flagged not fixed — containment checks ignore GPS accuracy.** `ContainmentChecker.isWithin()` compares raw lat/lon distance against `venue.radiusMeters` only; it never looks at `Location.accuracy` (the uncertainty radius `FusedLocationProvider` actually reports alongside every fix). This affects both the "already inside" fast path and `GeofenceBorderPoller` above, but matters most for the poller: near a 50m boundary that's already below Google's recommended minimum (see above), a single low-accuracy fix could read as "outside" from GPS jitter alone and force a real EXIT + stop scanning, even though the device hasn't actually left — and now that the poller no longer stops on a beacon sighting (see above), this can happen even while the beacon is actively being seen. A real fix would pad the effective radius by the fix's reported accuracy (or discard fixes above some accuracy threshold) before trusting a containment result. Not attempted here, out of scope for this pass.

## Beacon format: iBeacon

Decided: iBeacon (UUID + major + minor), because that's what the spec mentioned.

## RSSI smoothing: moving average (window 5)

Decided, over EMA or median, because it's simple, testable with fixture data, and the 4-bucket proximity output (Immediate/Near/Far/Unknown) doesn't have enough resolution to justify more precise tuning.

## Beacon-lost timeout: N = 5 seconds

Decided N = 5s mainly for fast feedback while developing/testing against a nearby advertiser — stop the advertiser and see "lost" within a few seconds instead of waiting around. `planning.md` §6 originally reasoned toward something closer to 10s (roughly 10x a typical 100ms–1s advertising interval), which is the more production-appropriate value: long enough to tolerate a couple of dropped packets or brief scan throttling without flapping to "lost" on every minor hiccup. Went with the shorter value here since quick iteration mattered more for this exercise; a real deployment would likely want it longer, closer to that original reasoning. `DEFAULT_BEACON_LOST_TIMEOUT` is a named constant specifically so this is trivial to retune later.

## UI: separate Geofence Log and Beacon Log, plus scrolling

The prompt's own sketch describes "a timestamped log of transitions and proximity changes" (singular), but this splits it into two separate, labeled logs instead. Geofence ENTER/EXIT and beacon proximity readings are different kinds of events at very different frequencies (a handful of geofence transitions vs. a steady stream of proximity readings while Inside) — interleaving them into one list makes either stream harder to scan at a glance. Both logs are still timestamped and live on the prompt's one required Compose screen. Added vertical scrolling to the screen now that there are two lists that can each grow past a small display's height (each capped at 20 entries, but that's still enough to need scrolling).

## Foreground service decision: foreground-only-while-Inside

Decided: `BroadcastReceiver` calls `startForegroundService()` on confirmed ENTER, `VenueMonitorService.stopSelf()` on confirmed EXIT. The service's lifetime is tied to the same Inside/Outside gate as the scanner itself, rather than an always-on foreground service or a plain background service. A plain background service was ruled out specifically because requirement 9's scenario (geofence transition firing with no UI alive) is exactly the condition Android's background execution limits and BLE scan throttling target. It risks silently going dark partway through an Inside session. Full option comparison and the background-service reasoning are in `planning.md` §8/§14.

## Module structure: stayed single-module

Considered splitting into a Gradle module per package (`:domain`, `:data-venue`, `:data-geofence`, `:data-ble`, `:data-location`, `:service`, `:ui`, plus `:app`) to better signal "built to extend." Estimated 3–5 hours for the full per-package split vs. 1.5–2.5 hours for a coarser 3-module version (`:domain`, `:data`, `:app`) — most of that cost is Gradle/Hilt friction, not moving files: this project already hit an AGP 9 "built-in Kotlin" vs. KSP incompatibility once (see Dependency injection above), and each additional Android library module carrying `@Inject`/`@Binds` would need the same fix repeated or centralized via a convention plugin; plus a real `api`/`implementation` visibility pass per dependency edge, and moving each fake into its owning module's own `test` source set instead of `:app`'s.

Decided against it, and kept the current single-module structure. Reasoning: the prompt is explicit that this is "one screen," 6–10 hours total, and structure is graded partly on *not* over-building — 8 Gradle modules for a single-screen app with no feature boundaries to enforce (there's nothing for a `:ui` or `:service` module to protect against) reads more like over-engineering than foresight to a reviewer, especially layered on top of a codebase that's still mostly `TODO()` stubs. A `:di` module also doesn't actually work as conceived — Hilt's `@Binds` graph needs to see every impl, so that wiring collapses back into `:app` regardless of how many modules exist below it. Full reasoning in the conversation; not written up in `planning.md` since nothing was implemented.

## Battery tradeoffs considered

- Scan filtering at the radio level (`ScanFilter` matching manufacturer data + UUID mask) rather than scanning unfiltered and discarding in the callback — cheaper than CPU-side filtering. Briefly removed mid-debugging on a misdiagnosis (see "Location permission" above), confirmed working and restored after the real root cause was found and fixed.
- Foreground-service-only-while-Inside instead of always-on, so the radio/scanner overhead is bounded to the time actually spent inside a venue.
- The extra exit check triggered by beacon loss (`GeofenceExitPoller`) could cause extra battery drain from manually checking location, but it could also save battery by stopping the scan sooner than waiting for the OS's opportunistic geofence EXIT. Further testing would be required to determine if it's truly worth it for battery life, but it does help meet the "don't scan outside the geofence" requirement.
- Activity Recognition as an optional stretch goal to duty-cycle scan aggressiveness (`LOW_LATENCY` while walking, `BALANCED`/`LOW_POWER` while still) — explicitly not required, only attempted if time remains; see `planning.md` §9.

## What I'd do with another week

To be filled in more fully once the core implementation is further along — premature to speculate in depth before the pending decisions above are settled and something is actually built against them. Items already known:

- Revisit the coarse 3-module split (`:domain`, `:data`, `:app`) above once the interfaces have stopped moving — worth doing once, not worth doing speculatively now.
- Consider using Activity Monitoring to help supplement the geofence ENTER/EXIT transitions with a more responsive "likely leaving" signal, so the scanner can be stopped sooner than waiting for the OS's opportunistic geofence EXIT. Would require a careful design pass to avoid false positives (e.g. walking past a venue without entering it) and to ensure it doesn't conflict with the existing geofence logic.
- **Site-calibrated distance heuristics.** `DistanceEstimator`'s log-distance path-loss model (`domain/DistanceEstimator.kt`) uses a fixed generic `pathLossExponent` (default 2.0, free-space). A real venue has walls, shelving, bodies, other 2.4GHz traffic — all of which distort RSSI in ways a single hardcoded exponent can't capture. With more time, worth computing that exponent (or a richer per-venue calibration curve) from actual measurements taken in the real deployment space — e.g. walking a known distance from the beacon and fitting the curve to observed RSSI — rather than assuming one constant works everywhere. Would meaningfully improve proximity-bucket accuracy in real, interference-heavy environments instead of just the open-air conditions this was tested in.
- Other calibration for the RSSI-to-distance model and smoothing, e.g. per-venue `txPower` (RSSI at 1m) and/or a more complex curve than the simple log-distance model, to better reflect real-world conditions
- More in-field testing and troubleshooting. As it is, it doesn't reliably begin scanning after exiting and then re-entering a geofence.
- Consider adding something to restart the scanning like the timer that stops it. Since the project emphasized not scanning outside the geofence, I focused on that. But you could utilize the knowledge that geofences update every 5ish minutes and continue checking at a shorter interval if someone has come back inside a geofence in that 5 minutes or stop tracking if they're clearly moving away.
- Consider a state machine that leverages geofence transitions, beacon proximity, location checks on 5 minutes timers, and the activity monitor to determine whether the user is in or outside a geofence.
- To get faster enter transitions, set up an outer geofence with a larger radius (e.g. 100m) that triggers a scan for the inner geofence (e.g. 50m). This would allow the app to start scanning sooner when the user is approaching the venue, rather than waiting for the inner geofence to trigger. The GeofenceBorderPoller could be used to do this.
- Add better code and testing for multiple venues (especially if trying implement the inner and outer geofence idea above). Also, you could just extrapolate outer geofences if they aren't provided.
- Possibly update border poller to use activity/location to determine if the user is moving away from the venue so polling can be stopped sooner
